# P6 TUI Shell

## 1. Background

P5 improved the line-oriented CLI with status, view modes, path autocomplete, and folded diff output. The next step is to make `mycli` feel closer to Claude Code in daily interactive use: a full-screen terminal UI with a rendered transcript, compact execution progress, completion popups, and temporary overlays.

This P6 slice changes the interactive shell experience only. It must reuse the existing `TurnService`, runtime stream events, slash command handlers, session service, and P5 render/status helpers where practical. It must not change model-visible context, provider protocols, tool semantics, session history format, or safety policy.

## 2. Goals

### 2.1 Default TUI entrypoint

Running `mycli` in an interactive terminal should launch the TUI by default.

Fallback behavior:

- If stdin/stdout are not interactive, use the existing line-oriented/plain behavior.
- Add an explicit plain mode flag, e.g. `mycli --plain`, for tests, pipes, and fallback terminals.
- Keep existing evaluation flags and non-interactive command paths working without requiring a TUI.

### 2.2 Startup welcome screen

Show a Claude Code-like welcome panel before the first prompt.

Required content:

- `mycli` version.
- Welcome text.
- Neutral default mycli ASCII mark.
- Current model.
- Billing/API mode when known.
- Workspace path.
- Tips for getting started.
- What's new / release notes hints.

Visual rules:

- Add restrained color accents for headings, commands, model, and prompt marker.
- Do not show recent sessions on the welcome screen.
- Do not make `/resume` special on the welcome screen; it remains a normal slash command.
- The welcome screen must not be appended to model-visible history or session transcript.

Easter egg:

- Support optional zodiac ASCII startup marks through configuration, e.g. `tui_startup_mark = "rabbit"` or `"random-zodiac"`.
- Zodiac marks are optional and not the default production look.
- Avoid emoji width dependencies; use terminal-safe ASCII.

### 2.3 Main layout

The main TUI is conversation-first:

- No right sidebar.
- No dense top status bar.
- Main area is a scrollable transcript.
- Bottom area contains the input box.
- Persistent bottom status is split:
  - left: workspace name/path
  - right: model name and context-window usage

Context status must show used tokens and total context window tokens:

```text
context 3,566 / 12,000 tokens
```

Percentage can be shown in `/status` overlay, but should not be required in the persistent status line.

### 2.4 Transcript rendering

The transcript should visually resemble Claude Code rather than labeled dashboard cards.

Rules:

- Do not show visible `USER`, `ASSISTANT`, `TOOL`, or `REASONING` labels in normal transcript rendering.
- Use subtle prompt markers, indentation, opacity, spacing, and folded blocks to distinguish item types.
- Keep one neutral surface style. Do not use many colored cards.
- Reserve stronger visual emphasis for errors, warnings, and approval prompts.

Internal typed rendering is still required:

```text
TuiTranscriptItem(type=user|assistant|thinking|tool_summary|diff|warning|error|approval)
```

The type drives rendering and accessibility, but the normal UI does not expose role labels as headings.

### 2.5 Claude-like execution path

During the agent action phase, show a compact execution path instead of dumping every raw tool call and tool result.

Examples:

```text
Thinking... (12s)
Reading files... (19s)
Running tests... (37s)
Editing files... (44s)
Waiting for approval... (52s)
```

Rules:

- One live status row represents the current turn.
- The label changes as phase changes.
- The elapsed time is total time since this turn started, not per-phase time.
- Recent tool activity can appear in a small rolling summary:

```text
Read src/mycli/cli/main.py
Read src/mycli/cli/rendering.py
Read docs/superpowers/specs/2026-05-25-p5-cli-experience.md
... 4 more reads folded
```

- Large tool results, command output, logs, and diffs are summarized or folded by default.
- Folded details can later be opened through an overlay.
- The execution path must update live as runtime events arrive, but it should remain curated and compact.

### 2.6 Final answer streaming and rendering

Final assistant output starts after the agent finishes its tool/action phase and is ready to answer.

Rules:

- Do not interleave final answer streaming with the compact execution path in a way that makes the transcript hard to scan.
- When final answer streaming begins, append deltas into the current assistant answer block.
- On turn completion, render the final `assistant_message` as the authoritative answer.
- If streamed text and final answer are equivalent, do not duplicate the answer.
- If the final answer differs from the streamed buffer, replace/update the current assistant block with the final answer.

Final answer rendering should support:

- paragraphs
- lists
- inline code
- fenced code blocks
- tables when practical
- syntax-highlighted code blocks if supported by the TUI framework

### 2.7 Input completion

The TUI input supports inline suggestions.

Slash commands:

- Typing `/` opens slash command suggestions.
- Typing `/` plus letters filters suggestions by prefix.
- Up/down arrows move selection.
- `Tab` inserts the selected command into the input but does not execute it.
- `Enter` sends the current input and then executes it.
- `Esc` closes suggestions without changing input.

Path completion:

- `@path` popup suggestions should reuse the P5 workspace-local path candidate behavior.
- Suggestions must not escape the workspace.

Slash command candidate set:

Required first-slice commands:

```text
/help
/status
/context
/usage
/view
/view default
/view verbose
/view focus
/resume <session>
/sessions
/quit
```

Existing workflow/inspection commands should remain available in suggestions:

```text
/tools
/bashes
/changes
/undo
/plan
/subagents
/subagents <child_session_id>
/memory
/trace
/fork [source] <new-session> [message-index]
```

TUI-only commands for this slice:

```text
/clear          clear current TUI transcript view without deleting session history
/theme          show or switch TUI theme
/mark <name>    switch optional startup ASCII mark, including zodiac marks
/release-notes  open what's-new overlay
```

Deferred commands:

```text
/model          model picker; requires provider model listing
/init           project instruction initialization; involves file creation flow
/diff           interactive diff overlay; useful but can follow after core TUI
```

Interrupt semantics:

- If the user presses `Ctrl+C` before sending, cancel the current edit and return to the prior stable input state.
- If the user presses `Ctrl+C` while a turn is running, interrupt the turn and restore the input text from just before send so it can be edited and resent.
- Interrupted partial assistant output must not be treated as a completed final answer.

### 2.8 Overlays

Use temporary overlays for informational commands rather than permanent side panels.

First slice overlays:

- `/help`
- `/context`
- `/usage`
- `/status`

Allowed later overlays:

- diff details
- large tool result details
- session list

Overlay rules:

- `Esc` closes the overlay.
- Overlays do not enter model-visible history.
- Overlays should not mutate runtime state unless the slash command itself is stateful.

### 2.9 Resume command

`/resume` remains a normal slash command in the TUI.

Behavior:

- `/resume <session>` loads historical session state.
- Resumed history renders into the transcript using the TUI transcript renderer.
- `/sessions` can be shown as a normal command/overlay, but no recent-session picker belongs on the startup welcome screen in this slice.

## 3. Technical Direction

Use `textual` for the first TUI implementation.

Rationale:

- Full-screen terminal layout, scrollable transcript, bottom input, keybindings, and overlays are first-class concepts.
- It avoids hand-rolling curses layout and keyboard handling.
- It has testing support for UI behavior.
- The project already accepts focused dependencies when they provide clear long-term value; TUI is one of those cases.

Add `textual` explicitly in the implementation plan after checking the current release's compatibility with Python 3.13 and existing `rich>=15.0.0`. The plan must record the chosen version/range and why it is compatible.

## 4. Proposed Components

### 4.1 `mycli.cli.tui.app`

Owns the Textual app shell:

- startup welcome screen
- transcript view
- input widget
- bottom status
- overlays
- keybindings

It should delegate runtime work to application services rather than importing provider/runtime internals directly.

### 4.2 `mycli.cli.tui.transcript`

Converts domain/runtime outputs into display items:

```python
@dataclass(slots=True, frozen=True)
class TuiTranscriptItem:
    kind: TuiTranscriptKind
    text: str
    metadata: Mapping[str, object] = field(default_factory=dict)
```

Responsibilities:

- map `TurnResponse`, `TurnRecord`, and `RuntimeStreamEvent` into TUI item types
- summarize tool events
- fold large tool/diff output
- preserve enough metadata for overlays

### 4.3 `mycli.cli.tui.completion`

Owns completion state:

- slash command candidates from existing command list
- prefix matching
- selected index
- tab accept without execute
- `@path` candidates via existing `path_completion_candidates()`

### 4.4 `mycli.cli.tui.status`

Formats bottom status fields:

- workspace
- model
- context used / total tokens

It may reuse `TurnService.inspect_status()` or a smaller structured status method if text parsing becomes brittle.

### 4.5 `mycli.cli.tui.overlays`

Displays `/help`, `/context`, `/usage`, `/status`, and later diff/tool details.

Overlay content should reuse existing service inspection methods where possible.

## 5. Non-Goals

- No right sidebar.
- No multi-pane dashboard.
- No full command palette in the first slice.
- No `/model` picker in the first slice.
- No `/init` project-file creation flow in the first slice.
- No interactive `/diff` command in the first slice.
- No recent-session picker on the welcome screen.
- No voice mode.
- No vim/editor mode.
- No model/runtime protocol changes.
- No session history format migration.
- No raw dump of every tool call/result in the main transcript.
- No browser UI; this is terminal TUI only.

## 6. Acceptance Criteria

- Running `mycli` in an interactive terminal starts the TUI.
- Running `mycli --plain` starts the existing line-oriented REPL.
- Non-interactive stdin/stdout does not force a TUI.
- Startup welcome screen renders with version, tips, what's new, model, billing/API mode, workspace, and neutral mark.
- Optional zodiac startup mark config works without changing default.
- Main transcript has no visible role labels and uses Claude-like compact rendering.
- Bottom status shows workspace, model, and `context used / total tokens`.
- Current-turn status line changes phase text and elapsed time as the turn progresses.
- Tool activity is summarized and folded rather than dumped.
- Final answer streams only after the action phase and renders Markdown/rich output.
- `/` slash suggestions support prefix filtering, arrow selection, Tab accept, Enter execute, and Esc close.
- Slash suggestions include required first-slice commands, existing workflow/inspection commands, and TUI-only `/clear`, `/theme`, `/mark`, and `/release-notes`.
- `@path` suggestions work and stay inside workspace.
- `Ctrl+C` interrupts running turns and restores pre-send input.
- `/help`, `/context`, `/usage`, and `/status` display through overlays.
- `/resume <session>` loads and renders historical session content.
- Existing line-oriented CLI tests continue to pass.
- TUI behavior has focused tests for completion, status formatting, event-to-transcript mapping, and key interrupt semantics.

## 7. Open Risks

- Existing runtime stream events may not expose enough structured information for high-quality tool summaries. The implementation should add a thin TUI adapter layer first and only widen runtime events if tests prove the gap.
- Final-answer-only streaming depends on distinguishing action-phase events from final response events. If provider adapters emit ambiguous `text_delta` events, the TUI should buffer conservatively and render final `assistant_message` as authoritative.
- `textual` dependency/version must be checked against Python 3.13 and existing Rich constraints before implementation.
- Interrupt behavior must coordinate with the existing runtime cancellation path. If runtime cancellation is not yet granular enough, P6 should display interrupted state and restore input while leaving deeper cancellation improvements to a follow-up.

## 8. Verification Plan

Implementation should include:

- Unit tests for slash and path completion.
- Unit tests for TUI status formatting.
- Unit tests for runtime event to transcript item conversion.
- Unit tests for execution path folding/summarization.
- Textual app tests for:
  - startup render
  - input completion keyboard behavior
  - overlay open/close
  - Ctrl+C input restoration
- Existing full verification:

```bash
uv run ruff check src tests
uv run mypy src/mycli
uv run pytest -q
```
