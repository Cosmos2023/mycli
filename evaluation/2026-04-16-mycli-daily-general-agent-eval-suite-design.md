## 1. 这份文档要解决什么问题

当前 `mycli` 的长期目标已经比较明确：

`它不应该只是一个会总结项目、读代码、改代码的 CLI，而应该成为一个能协助日常工作、承接多类任务的通用个人 AI assistant。`

如果目标是这样，那么评测方式也不能继续只围绕：

- 会不会搜索仓库
- 会不会修改代码
- 会不会调用几个工具

而应该转向一个更贴近真实工作的评测问题：

`当用户把它当成日常助手来使用时，它是否能在多轮交互中理解意图、记住约束、合理用工具、跨上下文继续推进，并最终交付一个可信结果？`

这份文档的目的，就是把这个问题收敛成一套可执行的场景化评测设计。

## 2. 设计原则

这套评测不追求“像学术 benchmark 一样覆盖所有可能”，而是优先满足 `mycli` 这个产品阶段最需要的几件事。

### 2.1 场景必须贴近日常工作

优先覆盖：

- 对话回复
- 文档与资料查找
- 结构化数据整理
- 小范围文件修改
- 中断恢复
- 调研与推荐
- 多文件复合协同任务

避免只出：

- 数学题
- 纯网页闯关题
- 只和代码库有关的题

### 2.2 每个场景都必须是多轮任务

单轮问答很难测出：

- 记忆是否稳定
- 限制是否会被遗忘
- 任务切换后能否恢复
- 新约束加入后能否更新策略

因此每个题目至少应包含 `4-5` 轮对话。

### 2.3 同时测“结果”和“过程”

不能只看最后答案对不对，还要看：

- 是否该用工具时用了工具
- 是否引用了证据
- 是否无谓探索
- 是否遗忘前文约束
- 是否在中断后还能恢复正确上下文

### 2.4 通用性优先于任务特化

设计时要始终避免把评测收窄成：

`测一个仓库专用 agent`

或者：

`测一个办公文本生成器`

更准确的定位应该是：

`测一个通用个人工作助手在真实日常任务中的综合 agent 能力`

## 3. 可借鉴的公开 benchmark

下面这些公开 benchmark 值得借鉴，但不应直接照搬。

### 3.1 GAIA

参考来源：

- https://arxiv.org/abs/2311.12983
- https://huggingface.co/gaia-benchmark

值得借鉴的点：

- 任务面广，不局限于某一个专业域
- 问题对人类来说往往“看起来简单”，但对 agent 来说需要真正理解、查找、推理和组合工具
- 强调通用 agent 的真实完成能力，而不是单一问答能力

不适合直接照搬的点：

- 部分题更偏开放世界信息查找，不完全贴合 `mycli` 的本地工作流定位

### 3.2 tau-bench

参考来源：

- https://arxiv.org/abs/2406.12045
- https://github.com/sierra-research/tau-bench

值得借鉴的点：

- 强调多轮对话中的工具调用与约束遵守
- 关注 agent 在与用户来回澄清时，是否能逐步收敛到正确执行路径
- 适合借鉴其“多轮 conversation + tool + policy”结构

不适合直接照搬的点：

- 原始场景偏行业流程模拟，和 `mycli` 的个人工作助手定位仍有距离

### 3.3 WorkArena / WorkBench

参考来源：

- https://github.com/ServiceNow/WorkArena
- https://arxiv.org/abs/2405.00823

值得借鉴的点：

- 更贴近知识工作与办公室任务
- 任务通常有清晰目标、环境状态和可验证结果
- 适合借鉴其“把办公任务做成可自动判分 task”的方法

不适合直接照搬的点：

- WorkArena 更偏 browser/enterprise software 环境，`mycli` 当前更适合先做本地文件与轻联网任务

### 3.4 OSWorld

参考来源：

- https://os-world.github.io/

值得借鉴的点：

- 强调长链路任务、跨应用执行、真实环境操作
- 对“只会说不会做”的 agent 有很强区分度

不适合直接照搬的点：

- `mycli` 当前主要 surface 仍是 CLI，不应为了 benchmark 强行做桌面 GUI 操作模拟

### 3.5 SWE-bench Verified

参考来源：

- https://www.swebench.com/

值得借鉴的点：

- 修改类任务不能只看描述，要看真实变更和验证结果
- 对 `mycli` 的“轻量文件修改任务”设计非常有价值

不适合直接照搬的点：

- 它聚焦软件工程，不能代表 `mycli` 作为通用助手的全貌

### 3.6 LongMemEval / LoCoMo

参考来源：

- https://arxiv.org/abs/2410.10813
- https://arxiv.org/abs/2402.17753

值得借鉴的点：

- 记忆能力不能只测“有没有上下文窗口”，而要测：
  - 是否能记住历史事实
  - 是否能做跨轮时序推理
  - 是否能识别新信息覆盖旧信息
  - 不确定时能否克制、不瞎编

不适合直接照搬的点：

- 原始 benchmark 偏研究型长记忆测试，仍需转译成更办公化、更短链路但高信号的任务

### 3.7 结论

对 `mycli` 最适合的借鉴组合不是单一 benchmark，而是：

`GAIA 的通用性 + tau-bench 的多轮工具交互 + WorkArena/WorkBench 的办公任务形态 + LongMemEval 的记忆维度`

## 4. 评测套件总体结构

建议把这套评测命名为：

`mycli Daily General-Agent Eval Suite`

建议由 `7` 个场景组成，按难度从低到高推进。

每个场景都应具备：

- 明确的用户目标
- 至少 `4-5` 轮对话
- 至少一个“新限制注入”回合
- 至少一个“记忆/恢复/追问”回合
- 可验证结果
- 可记录的工具轨迹

## 5. 七个场景题

## 5.1 场景一：老板消息回复助手

**难度：** 低

**任务类型：** 对话、风格控制、约束记忆

**目标：** 测试 agent 是否能在没有复杂工具的情况下理解沟通语境、记住风格约束，并在多轮中持续保持一致

**推荐素材：**

- 一段背景说明
- 一组用户个人沟通偏好
- 一条老板原始消息

**推荐对话流程：**

1. 用户先告诉 agent：
   - 老板比较看重结果
   - 不喜欢过度解释
   - 回复里不要出现“尽量”“大概”“可能”
2. 用户给出老板消息，让 agent 起草一个简短回复
3. 用户补充：
   - 不要提预算问题
   - 语气再坚定一点
4. 插入一轮无关小问题后，再回来要求：
   - 按刚才的风格，再写一条催进度消息
5. 最后一轮要求：
   - 给出“正式版”和“更口语版”两个版本

**主要考点：**

- 语义理解
- 风格持续性
- 跨轮记忆
- 被打断后恢复
- 不用工具时的克制

**自动/半自动判分点：**

- 是否出现禁用措辞
- 是否违反“不提预算”
- 是否保留“简短、结果导向”的风格

---

## 5.2 场景二：制度与资料查找

**难度：** 低到中

**任务类型：** 本地检索、证据引用、跨文件综合

**目标：** 测试 agent 是否能正确查找本地文档、引用出处，并把检索结果转成可用解释

**推荐素材：**

- `expense-policy.md`
- `travel-policy.md`
- `meeting-notes.md`
- `faq.md`

**推荐对话流程：**

1. 用户询问一个具体制度问题，例如：
   - 高铁二等座是否可报销
   - 出差住宿标准是多少
2. 用户追问：
   - 结论依据在哪一份文件、哪一节
3. 用户再问：
   - `travel-policy` 和 `faq` 是否有冲突
4. 用户要求：
   - 帮我写一段发给同事的说明话术，语言不要太官腔
5. 最后一轮故意加入一个文档里没有的信息，看 agent 是否会编造

**主要考点：**

- 文件检索能力
- 引用与证据意识
- 事实与推测区分
- 跨文件冲突发现
- 不知道时能否明确说不知道

**自动/半自动判分点：**

- 引用文件是否正确
- 关键制度数字是否准确
- 面对缺失信息时是否幻觉

---

## 5.3 场景三：周报数据整理与异常解释

**难度：** 中

**任务类型：** 结构化数据处理、文本生成、追问解释

**目标：** 测试 agent 是否能用工具处理表格类数据，并把数据结论稳定延续到后续文本任务中

**推荐素材：**

- `weekly_sales.csv`
- `support_tickets.csv`
- `team_hours.csv`

**推荐对话流程：**

1. 用户要求：
   - 总结本周核心数据
   - 找出三个异常点
2. 用户追问：
   - 为什么你认为某项是异常
3. 用户要求：
   - 基于这些数据写一份经理周报，语气稳健一些，不要过度乐观
4. 用户补充一个限制：
   - 不要提某位员工名字
5. 用户最后再问：
   - 如果老板追问“哪个异常最需要下周优先处理”，你怎么回答

**主要考点：**

- 计算与统计正确性
- 工具调用能力
- 数据结论到自然语言写作的迁移
- 新约束注入后的文本更新
- 追问解释能力

**自动/半自动判分点：**

- 汇总数字是否正确
- 异常点是否与数据一致
- 后续文案是否保持前文数据结论

---

## 5.4 场景四：小范围修改任务

**难度：** 中

**任务类型：** 代码/配置理解、精确编辑、验证

**目标：** 测试 agent 是否能完成现实中的“小修小补”任务，而不是只会给建议

**推荐素材：**

- 一个小型 repo 或脚本目录
- 一个可复现的 bug / 配置错误
- 对应测试或 smoke 脚本

**推荐对话流程：**

1. 用户描述一个具体问题：
   - 某个脚本输出路径错了
   - 某个配置字段没生效
2. 用户追加限制：
   - 不要改 CLI 参数接口
   - 不要引入新依赖
3. 用户再要求：
   - 顺手补一条测试或更新说明文档
4. 用户追问：
   - 你具体改了哪里
   - 怎么验证没有破坏别的行为
5. 最后一轮要求 agent 给出简明变更摘要

**主要考点：**

- 读代码和找点修改能力
- 约束遵守
- 编辑后验证
- 面向用户解释改动
- 工具链纪律

**自动/半自动判分点：**

- 文件 diff 是否合理
- 测试/脚本是否通过
- 是否违反“不要改接口”等限制

## 5.5 场景五：中断后的任务恢复

**难度：** 中到高

**任务类型：** 多轮记忆、任务切换、上下文恢复

**目标：** 专门测 agent 的会话记忆、多轮连续性和工作上下文管理

**推荐素材：**

- 一份待办清单
- 一份项目背景说明
- 一个中途插入的无关任务

**推荐对话流程：**

1. 用户先让 agent：
   - 基于待办清单整理一个今天的行动计划
2. 用户再补充两个限制：
   - 下午两点前不能安排外部会议
   - 优先推进 A，不要先碰 B
3. 中途突然插入一个无关问题，例如：
   - 帮我润色一条请假消息
4. 再切回主任务，要求：
   - 继续刚才的行动计划，并考虑我下午要留 1 小时处理突发问题
5. 最后追问：
   - 你刚才为什么把 A 放在 B 前面

**主要考点：**

- 是否保留原始任务状态
- 是否记住时间限制和优先级
- 中断后的恢复质量
- 是否能解释自己的任务排序

**自动/半自动判分点：**

- 恢复后是否还保留 A/B 优先关系
- 是否违反时间约束
- 是否把中途无关问题污染主任务

## 5.6 场景六：外部调研与推荐

**难度：** 高

**任务类型：** 联网检索、来源引用、约束更新、决策建议

**目标：** 测试 agent 在开放世界信息检索中的真实表现，以及是否能用证据支持推荐

**推荐素材：**

- 用户需求描述
- 预算、地点、偏好等约束

**推荐对话流程：**

1. 用户提出调研任务，例如：
   - 比较三个会议酒店
   - 比较三个 API 服务
   - 给出差行程做推荐
2. 用户要求：
   - 附上来源
   - 区分事实和你的建议
3. 用户中途改约束：
   - 预算收紧
   - 地区变化
   - 更看重稳定性而不是价格
4. 用户追问：
   - 为什么放弃某个候选项
5. 最后要求：
   - 给出最终推荐和一个备选方案

**主要考点：**

- 实时检索
- 来源可信度
- 约束更新后的重排序
- 推荐解释力
- 不把过时或不确定信息说得过于肯定

**自动/半自动判分点：**

- 是否提供来源
- 结论是否与最新约束一致
- 是否说明放弃项原因

## 5.7 场景七：复合型协同任务

**难度：** 高

**任务类型：** 多文件、多轮、编辑与写作联动、全局上下文管理

**目标：** 测试 `mycli` 是否已经初步具备“多面手日常助理 agent”的雏形

**推荐素材：**

- `meeting-notes.md`
- `tasks.json`
- `contacts.csv`
- 一个小型项目目录
- 一份昨日决议记录

**推荐对话流程：**

1. 用户要求：
   - 看会议纪要和任务表，找出 3 个 blocker
2. 用户继续要求：
   - 更新任务文件，标记 owner 和 next step
3. 用户再要求：
   - 分别起草一条发给老板、一条发给同事的跟进消息
4. 用户故意隔一轮后追问：
   - 刚才谁负责 X
   - 你为什么把 Y 归类成 blocker
5. 用户最后要求：
   - 给我一个明天的优先级建议，控制在 5 条以内

**主要考点：**

- 多文件综合
- 工具与编辑联动
- 长链路上下文维护
- 对不同对象的表达切换
- 全局任务理解与收敛

**自动/半自动判分点：**

- blocker 是否与材料一致
- owner/next step 写回是否正确
- 后续消息内容是否与修改后的状态一致

## 6. 评分维度

建议总分为 `100` 分。

### 6.1 任务完成度（30 分）

看 agent 是否真的完成了用户目标，而不是只给了方向性建议。

评分关注：

- 任务是否收口
- 产出是否可直接使用
- 是否遗漏用户要求中的关键部分

### 6.2 正确性与可核验性（20 分）

看结果是否正确、是否能被文件、数据、引用或验证命令支撑。

评分关注：

- 数据、事实、引用是否正确
- 修改类任务是否真的改对
- 是否给出足够证据支持结论

### 6.3 记忆与跨轮延续（15 分）

看 agent 是否能记住前文中仍然有效的约束与事实。

评分关注：

- 是否遗忘风格要求
- 是否遗忘前文限制
- 是否能在中断后恢复主任务

### 6.4 工具选择与调用质量（15 分）

看 agent 是否在正确的时候使用正确的工具，并正确吸收结果。

评分关注：

- 该搜索时是否搜索
- 该编辑时是否编辑
- 该不联网时是否克制
- 是否出现无谓、重复、低价值工具调用

### 6.5 上下文管理（10 分）

看 agent 是否能处理插话、改需求、补约束和任务切换。

评分关注：

- 是否把新限制覆盖到后续结果
- 是否能区分主任务与插入任务
- 是否能保持任务边界清晰

### 6.6 语义理解与澄清（5 分）

看 agent 是否理解真实意图，并只在必要时做最小澄清。

评分关注：

- 是否抓住用户真正想解决的问题
- 遇到歧义时是否澄清得恰到好处
- 是否没有被字面措辞带偏

### 6.7 协作体验（5 分）

看 agent 的交互是否像一个靠谱同事，而不是一个会输出很多字的模型。

评分关注：

- 表达是否清晰
- 是否区分事实与建议
- 是否主动暴露不确定性和风险

## 7. 评级标准

建议按下面四档收口。

### 7.1 90-100 分

`接近可投入真实日常工作的通用个人助理 agent`

表现特征：

- 大多数任务能独立完成
- 多轮记忆稳定
- 工具调用克制且有效
- 几乎不会因为上下文漂移而失真

### 7.2 75-89 分

`已具备较强实用价值，但仍需要用户做结果复核`

表现特征：

- 大部分任务可用
- 偶尔遗忘约束或出现探索冗余
- 关键任务仍需人工把关

### 7.3 60-74 分

`能做部分工作，但距离“多面手 agent”仍有明显差距`

表现特征：

- 单项能力可能不差
- 但跨轮延续、工具纪律或上下文恢复不稳定

### 7.4 60 分以下

`仍偏“会聊天或会局部做事的工具”，尚未形成稳定 agent 能力`

表现特征：

- 容易遗忘限制
- 工具调用随意
- 任务推进经常跑偏

---

## 8. 执行协议建议

为了让这套评测后续可以产品化，建议每个场景都标准化成以下结构。

### 8.1 场景素材包

每个场景对应一个固定目录，至少包含：

- 场景说明
- 初始输入文件
- 多轮用户脚本
- 隐藏参考答案
- 可自动检查的断言

### 8.2 多轮脚本

每题固定 `4-5` 轮用户输入。

脚本中应明确：

- 哪一轮加入新约束
- 哪一轮插入扰动问题
- 哪一轮追问依据或恢复上下文

### 8.3 trace capture

除结果外，还应记录：

- 工具调用序列
- 关键中间回答
- 是否引用证据
- 是否发生约束遗忘

### 8.4 双层判分

建议采用：

1. **确定性检查**
   - 文件 diff
   - 数字答案
   - 测试结果
   - 是否命中关键词或禁用词
2. **rubric 打分**
   - 记忆质量
   - 协作体验
   - 上下文管理
   - 工具选择质量

### 8.5 隐藏扰动回合

建议在至少 `4` 个场景里加入隐藏扰动，例如：

- 突然更改优先级
- 插入无关任务
- 新信息覆盖旧信息
- 追问早先提过的细节

这样能更好区分：

- 只是“会当前轮回答”的模型
- 真正具备跨轮连续性的 agent

---

## 9. 这套评测最想帮 mycli 看清什么

如果这套评测后续真的跑起来，它最核心的价值不是给出一个漂亮分数，而是帮助 `mycli` 回答下面几个更重要的问题：

1. `mycli` 现在到底更像是一个会调用工具的模型，还是一个真正能跨轮推进工作的 agent
2. `mycli` 的主要短板到底在：
   - 记忆
   - 工具调用
   - 任务收口
   - 上下文管理
   - 语义理解
3. 当前的 runtime 演进，是否真的在把它往“通用个人 AI assistant”推进，而不是往“仓库任务优化器”推进

因此，这套评测应被当作：

`mycli 通用 agent 化过程中的产品化验收面`

而不是一次性的 demo 题库。

## 10. 后续建议

建议按下面顺序继续推进。

1. 先把这 `7` 个场景做成文档级基线
2. 再为每个场景补固定素材目录和多轮脚本
3. 再补自动检查器与 rubric 评分模板
4. 最后把它们接成可重复运行的 `mycli` 评测执行框架

更进一步时，还可以扩展两条支线：

- **长期记忆支线**
  - 把跨 session 的偏好保持和事实记忆纳入评测
- **助手自动化支线**
  - 引入更完整的任务执行、审批和恢复链路

## 11. 一句话总结

这套评测的核心思想不是“再给 `mycli` 出几道题”，而是：

`用一组贴近日常工作的多轮场景，系统性检验 mycli 是否正在成长为一个真正通用、可靠、能协助用户持续推进任务的个人 assistant agent。`
