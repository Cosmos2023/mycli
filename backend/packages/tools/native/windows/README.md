# Windows sandbox helper

Release builds place `mycli-windows-sandbox.exe` in this directory. The Node
runtime resolves the helper from the packaged `@mycli/tools` assets. The helper
validates the protocol request and setup state before restricted commands can
run. A capable host without a legacy installation selects PSEC; setup needs no elevation or
dedicated accounts. Unsupported hosts and existing account installations retain the restricted-token
backend. `--handshake` reports `backend=psec|restricted_token`; a PSEC marker pins that choice.

PSEC uses the pinned Microsoft schema and FlatBuffers C++ bindings generated by CMake. The build
pins both schema and dependency hashes. Distributed helper license files are included beside the
binary. No Rust runtime or compiler is required. Feature alignment, acceptance evidence and the
remaining inbound-loopback limitation are in [the feature report](../../../../../docs/parity/windows-sandbox-feature-parity.md).
Full PSEC details and compatibility limits are in
[Windows policy](../../../../../docs/windows.md#psec-compatibility-and-boundaries).

The helper's host-facing recovery operations are:

- `--handshake`: bounded, read-only protocol and setup state.
- `--check-host`: read-only PSEC capability check or legacy public-path compatibility check.
- `--ensure-setup`: serialize setup, request UAC when needed, and verify the result.
- `--reset`: reconcile recorded ACLs and clear credential/setup markers; refuse active helpers.
- `--repair`: stop processes, reconcile ACLs, refresh setup, and verify readiness.
- `--uninstall`: disable/stop owned accounts, remove tracked ACL/network state, profiles and accounts.

`--reset` intentionally preserves the dedicated local accounts and all firewall/WFP restrictions.
The public `mycli sandbox setup|reset|repair|uninstall` commands preview these operations and require `--confirm`;
users should not invoke the packaged helper directly.

PSEC translates protocol v2 directly into per-command filesystem and endpoint rules, uses a private
desktop granted only to that container, and retains job-based descendant cleanup. Protected absent
paths and hardlink aliases are prepared under the owner lock; empty placeholders are removed on
normal completion or later recovery. Host NULL DACLs do not grant PSEC writes and are never rewritten.
Writable roots are not enumerated at launch: a host-created hardlink alias inside a writable root
is accepted, which matches the shipped Codex Windows sandbox, and launch preparation stays
independent of workspace size. Denied, read-only and protected metadata trees still expand their
hardlink aliases before launch. Set `MYCLI_SANDBOX_PROFILE=1` to print per-phase launch timings to
stderr when investigating latency.

On the legacy backend, protocol v2 sends exact denied-read roots and an empty glob field: Node resolves globs before launch. `network=enabled` selects the online identity;
`network=disabled` selects the offline identity. A validated `network_proxy_port` selects a separate
proxy identity. All three keep the same restricted-token filesystem boundary. WFP's per-account
sublayers and per-logon dynamic exceptions prevent concurrent processes from sharing proxy authority.
The proxy exception is installed while the runner is suspended and is revoked when its host exits.

The legacy handshake verifies credentials, restricted-token creation, live firewall/WFP filters, and
host access to the proxy sublayer. It has no hard-coded ready flag. Setup/reset and ACL preparation
are serialized without serializing command execution. Reset preserves accounts and network denies.

Build with CMake/Visual Studio, run `ctest`, install the helper in this directory, then run the
Windows platform suite after `mycli sandbox setup --confirm`. The reusable Windows CI workflow
also exercises reset/reinitialization on its disposable runner. Restricted launch failure never
falls back to an unrestricted host process.

From a Visual Studio developer PowerShell at the repository root:

```powershell
$ErrorActionPreference = "Stop"
cmake -S native/windows-sandbox-helper -B native/windows-sandbox-helper/build -A x64
if ($LASTEXITCODE -ne 0) { throw "CMake configure failed" }
cmake --build native/windows-sandbox-helper/build --config Release
if ($LASTEXITCODE -ne 0) { throw "Native build failed" }
ctest --test-dir native/windows-sandbox-helper/build -C Release --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Native tests failed; do not install this helper" }
npm run promote:windows-sandbox-helper
if ($LASTEXITCODE -ne 0) { throw "Helper promotion failed" }
```

Promotion copies the Release helper into this directory, records
`mycli-windows-sandbox.sha256`, and refreshes the git-ignored vendored copy under
`backend/apps/mycli/dist/node_modules`. `release:verify --require-windows-helper`
checks the PE header, the x64 machine field and the recorded hash; the strict Windows
runner refuses to start when the manifest or the vendored copy is stale.

On a PSEC-capable host, configure with `-DMYCLI_REQUIRE_PSEC_TESTS=ON` so CTest also requires
`windows_psec`. This gate fails on an unsupported host instead of reporting a skipped enforcement
test. The reusable workflow explicitly runs that binary whenever its helper selects PSEC.

On a disposable Windows development machine, verify the checkout without starting GitHub CI:

```powershell
npm ci
if ($LASTEXITCODE -ne 0) { throw "Dependency installation failed" }
npm run dev -- sandbox setup --confirm
if ($LASTEXITCODE -ne 0) { throw "Sandbox setup failed" }
npm run dev -- sandbox status
if ($LASTEXITCODE -ne 0) { throw "Sandbox is not ready" }
$env:MYCLI_WINDOWS_SANDBOX_SETUP_TESTS = "1"
$env:MYCLI_WINDOWS_SANDBOX_MAINTENANCE_TESTS = "1"
npm run test:windows-sandbox
if ($LASTEXITCODE -ne 0) { throw "Windows isolation tests failed" }
```

Check each command's exit code before proceeding. Both opt-ins are required for release validation:
they exercise credential reset, repair, uninstall, and reinstallation, stopping sandbox processes
and modifying the dedicated accounts. The reusable Windows release gate enables both before
uploading its helper artifact.

Use Node 24, CMake >= 3.24, the Visual Studio C++ Build Tools and Windows SDK for x64.
The strict runner requires the original 13 passing tests and, when PSEC is selected, seven additional
parity tests. Both summaries must have no failures, skips, cancellations or todo
results. `$ErrorActionPreference` alone does not stop PowerShell 5.1 on native command failures;
the explicit exit-code checks above are required.

After all native and platform checks pass:

```powershell
npm run build
if ($LASTEXITCODE -ne 0) { throw "Application build failed" }
npm run release:verify -- --require-windows-helper
if ($LASTEXITCODE -ne 0) { throw "Release verification failed" }
npm run smoke:package -- --require-windows-helper --require-windows-ready
if ($LASTEXITCODE -ne 0) { throw "Installed package is not ready" }
```

This last command verifies the installed candidate against existing machine state. It does not
prove a clean installation. On a fresh Windows VM or dedicated test machine, add
`--setup-windows-sandbox --artifacts-dir release-evidence`; this requires setup to be absent,
performs setup through the installed CLI, then separately requires status `ready`.
See [the release guide](../../../../../docs/releasing.md) for retaining the tested tarball and evidence.

The initial 2026-09-17 legacy run was blocked by a host NULL DACL. The new PSEC backend has passed
the four native tests and all 13 real Windows tests on that same host, without changing the
third-party DACL. See [the local verification report](../../../../../docs/parity/windows-sandbox-local-verification.md)
for exact evidence and the remaining clean-host release gate.
A NULL DACL permits access to everyone, unlike an empty ACL. If the audit cannot safely apply a
deny, stop validation; do not suppress the audit, change third-party permissions, or claim that
compilation or a single `ready` response proves complete isolation.

See [Windows policy and maintenance](../../../../../docs/windows.md) for managed denied-read settings,
concurrent policy changes, upgrade limitations, and opt-in destructive maintenance tests.

After building, `npm run sandbox:check-host` diagnoses this host without installing the helper,
setting up accounts or requesting elevation. PSEC reports `psec_available` after actual environment
creation and startup-attribute checks. The legacy backend returns `host_null_dacl` for known NULL DACL
blockers, and `host_audit_incomplete` when inspection is partial. A zero exit means only that the
bounded inspection found no known blocker; it is not sandbox readiness or release acceptance.
See [host compatibility findings](../../../../../docs/parity/windows-sandbox-host-optimization.md)
for the two-phase audit and the isolated integrity experiment.
